# Phase 1: Block shell + View panel + terminal actions

## Context

Phase 1 lands the foundation that every later phase builds on: a registered Obsidian block class that the Rock startup chop swaps in for the WebForms `GroupDetail.ascx` block, plus a complete view-mode experience. By the end of Phase 1 the block renders an existing group with full chrome and design fidelity, the audit details modal works, and Delete / Archive / Copy all execute the same backend semantics the WebForms block did. Edit mode opens a placeholder page that Phase 3 fills in. Architectural decisions for this phase are governed by [00-architecture.md](00-architecture.md), which is now locked.

## Behavior delivered

- Visiting `/Group/{N}` (integer Id) or `/Group/{idKey}` loads the group and renders the redesigned view panel: header (icon, name, GroupType chip, Campus chip, follow star, Audit kebab), subheader (relationship strength label, optional Public chip, conditional tags), two-column body (Overview card on left, Group Tools card on right), and footer (Edit, Cancel, optional Copy, Security).
- The Overview card renders Description, Group Administrator (linked), Parent Group (linked), Schedule, Group Capacity, Goal of Group, Neighborhood, Privacy, Group Preference, plus a Linkages section listing Registrations / Event Item Occurrences / Content Items pulled from the same EF queries the WebForms Lava read.
- The Group Tools card renders the eight quick links (Attendance, Scheduler, RSVP, Placement, Map, History, Fundraising, Plus any group-type-conditional items) under "Participation" / "Views" sub-headers, conditional on each LinkedPage block setting plus the corresponding GroupType flag.
- Clicking the Audit kebab opens an Audit Details modal showing Created By, Modified By, and Id in three horizontal columns (per Q7 Figma).
- Clicking Edit transitions the panel into edit mode and shows a Phase 3 placeholder. Cancel returns to view mode.
- Clicking Copy opens the Copy modal with the warning text and the "Include Child Groups" checkbox **unchecked by default** (flipped from WebForms). Copy uses `GroupService.CopyGroup` and navigates to the new group.
- Clicking Delete prompts for confirmation, runs the Delete auth check, runs `GroupService.CanDelete` (showing the error if it fails), deletes any orphaned non-named Schedule, and routes through `DeleteSecurityRoleGroup` for security role groups. Navigation honors `returnUrl` (now validated as same-origin) or falls back to `GroupListPage` with the parent group expanded.
- Clicking Archive (when GroupHistory is enabled and history rows exist) prompts for confirmation, then either archives the group alone or, when child groups exist, prompts whether to cascade to descendants.
- Every Id-style page parameter the block emits is written as IdKey (per Q4): `GroupId` on the 11 outbound LinkedPage destinations, plus `RegistrationInstanceId` / `EventItemOccurrenceId` / `ContentItemId` / `SourceGroup` on the entity-specific destinations, plus `GroupId` on self-referential URLs like the breadcrumb. The 5 still-WebForms destinations on the `GroupId` path may emit broken links until Phase 7 ships; this is acknowledged.
- Quick-Return is registered for the loaded group via `addQuickReturn(name, "Groups", 20)` from `@Obsidian/Utility/page`.

## Behavior NOT delivered

- Edit form fields, validation, GroupType cascade, and the Save block action: **Phase 3**.
- Adding a new group from `/Group/0` (or via the GroupTreeView Add Root / Add Child paths): **Phase 3** (the Edit panel and Save body land together).
- Group attribute values render in the Overview card from data the bag already exposes; full attribute editing in the edit panel is **Phase 4**.
- Member attribute definitions panel: **Phase 4**.
- Group Requirements panel + modal: **Phase 5**.
- Group Sync panel + modal (including the Sync Frequency component restyle per Q9): **Phase 5**.
- Group Member Workflow Triggers panel + modal: **Phase 5**.
- Meeting Locations card with map cards (the per-`GroupLocation` 16:9 hover-to-expand design): **Phase 2**.
- Locations editing modal and inline schedule logic: **Phase 6**.
- Group Image hero region in the Overview card. The Vue partial wires up the conditional render in this phase, but the bag's `photoUrl` field is always null until Phase 2 ships the new `Group.PhotoId` column (per Q8). Until then the region always omits.
- Trailblazer-styled fields on the General section: **Phase 3** (per Q6 the only affected fields live in General).
- L2 (group-requirements duplicate-edit corruption): out of phase scope; tracked as a separate `/bugfix` spec per Q12.
- Updating the 5 still-WebForms outbound destinations to accept IdKey: **Phase 7** ("Update dependencies").

### 2026-05-07 — Collapsed Archive flow from 3 actions to 2; prompt-decision moved to Vue

User-driven post-self-review feedback questioned why the block needed three Archive actions (`Archive`, `ArchiveSingleGroup`, `ArchiveWithChildren`). Comparing back to the WebForms block confirmed only two real archive operations: `ArchiveSingleGroup` (parent only) and `ArchiveAllChildGroups` (cascade). The third action existed only because the original Obsidian design placed the children-check on the server and returned a `needsChildPrompt` discriminator that the Vue layer used to dispatch to one of two follow-up actions, costing a second round-trip on every children-archive. Refactored to **Design B**:

- `Archive(key)` always archives the parent only (no children guard, no discriminator). Mirrors WebForms `ArchiveSingleGroup` worker semantics.
- `ArchiveWithChildren(key)` unchanged — cascades through `GetAllDescendentGroups` then archives parent.
- `ArchiveSingleGroup` block action and the `ArchiveResponse` discriminator class are deleted.
- New `bag.HasChildGroups: bool` populated server-side in `GetCommonEntityBag` via `groupService.Queryable().Any( g => g.ParentGroupId == entity.Id )`. Mirrors the WebForms `btnArchive_Click` children check at [GroupDetail.ascx.cs:641](RockWeb/Blocks/Groups/GroupDetail.ascx.cs:641).
- Vue's `onArchiveClick` now reads `bag.hasChildGroups`: if true, opens the prompt modal (which resolves with the action name `"Archive"` or `"ArchiveWithChildren"`); if false, calls `Archive` directly. `showArchiveChildPrompt` resolves with the action name string instead of the redirect URL; `onArchiveSingle` / `onArchiveCascade` are now thin resolvers, not action invokers.

Result: single round-trip in both the children and no-children cases (vs the prior 2 round-trips when children existed), 2 block actions instead of 3, prompt-or-not decision made client-side from bag data — matching the typical Obsidian convention. Action names stay grep-able and audit-log-meaningful (`"Archive"` vs `"ArchiveWithChildren"`).

**Staleness consideration:** `HasChildGroups` is now bag-render-time, not click-time. If a child group is added concurrently between bag render and the user clicking Archive, the user could archive the parent without being prompted about the new child. The worst-case outcome is an active child under an archived parent (inconsistent, fixable, not corrupting). Group hierarchy edits are rare enough that this is acceptable; if it ever becomes a real concern, the `Archive` action could re-check server-side and log a warning. Out of scope for Phase 1.

**Reason:** the prior "server returns prompt discriminator → Vue calls follow-up action" flow was a holdover from the WebForms postback-modal-postback dance. Obsidian blocks dispatch UX from the client; that's where the prompt-or-not decision belongs. Affected code: [Rock.Blocks/Group/GroupDetail.cs](Rock.Blocks/Group/GroupDetail.cs) (`Archive` simplified, `ArchiveSingleGroup` deleted, `ArchiveResponse` deleted, `GetCommonEntityBag` adds `HasChildGroups`), [Rock.ViewModels/Blocks/Group/GroupDetail/GroupBag.cs](Rock.ViewModels/Blocks/Group/GroupDetail/GroupBag.cs) (new `HasChildGroups` property), [groupBag.d.ts](Rock.JavaScript.Obsidian/Framework/ViewModels/Blocks/Group/GroupDetail/groupBag.d.ts) (new field), [groupDetail.obs](Rock.JavaScript.Obsidian.Blocks/src/Group/groupDetail.obs) (`onArchiveClick`, `onArchiveSingle`, `onArchiveCascade`, `showArchiveChildPrompt`, `archiveResolution` ref type).

Setting that prop delivers identical UX with zero custom code. The 5 audit-related bag fields originally specified for the modal (`auditCreatedBy`, `auditCreatedDateTime`, `auditModifiedBy`, `auditModifiedDateTime`, `id`) were ultimately removed during the review pass because the framework fetches its own data via REST.

**Linkages query path corrected** (spec item 49). The spec referenced `ContentChannelItemAssociation` for content-item linkages; that table holds parent-child relationships between two `ContentChannelItem` rows and has no `GroupId` column. The actual chain the WebForms Lava walks is `Group.Linkages → EventItemOccurrenceGroupMap → EventItemOccurrence → EventItemOccurrenceChannelItem → ContentChannelItem`. Implementation uses the corrected chain at `BuildLinkages`. Spec text corrected in place.

**Archive flow uses 2 actions, not 3** (spec items 37-41). Self-review identified that the spec's `Archive` + `ArchiveWithChildren` design would loop forever on the "No" branch of the children prompt, and a third action `ArchiveSingleGroup` was added. The review pass collapsed the design back to 2 actions: `Archive` always parent-only (no children guard); `ArchiveWithChildren` cascades. The Vue layer reads `bag.HasChildGroups` and decides client-side whether to prompt. Single round-trip in both cases (down from 2). One accepted tradeoff: see "New latent bugs / TODOs surfaced" below for the staleness window.

**Outbound IdKey policy broader than spec** (Q4 audit). The spec scoped IdKey writing to "the 11 outbound LinkedPage destinations" (GroupId only). The post-self-review audit broadened this to every Id-style page parameter on every outbound URL: linkage URLs (`RegistrationInstanceId` / `EventItemOccurrenceId` / `ContentItemId`), self-referential URLs (breadcrumb `GroupId`, post-action navigation). [00-architecture.md](00-architecture.md) Q4 was updated in place to reflect the broader scope. Receiving destinations all accept IdKey today; verified during the audit.

**Breadcrumb "New Group" mislabel fixed** (spec item 4). The spec said mirror WebForms verbatim. The WebForms block returns "New Group" both for `?GroupId=0` (real Add) and for any `?GroupId=N` where the group can't be loaded (deleted, archived, malformed key). Implementation only shows the Add crumb for `groupId == 0` or empty Guid (real Add sentinel); a stale Id returns no crumb. Engineering note in code explains the divergence. UX bug, not parity worth preserving.

**Bag shape divergences from spec.** The user-driven review pass restructured several bag fields. `Administrator` and `ParentGroup` use new `GroupAdministratorBag` / `ParentGroupBag` types (with `Name` + pre-resolved `Url` honoring `EntityType.LinkUrlLavaTemplate`) instead of the spec's `ListItemBag` shape. The "GroupType chrome" fields (`GroupTypeName` + `GroupTypeIdKey` + `CanEditGroupType`) collapsed to a single `GroupDetailGroupTypeBag` with `Name` + auth-gated `Url`. `RelationshipStrengthLabel` (string) replaced by `RelationshipStrength` (typed enum from `Rock.Enums.Group`); the Vue side resolves the human-readable label via the auto-generated `RelationshipStrengthDescription` map. `Id` and the 4 audit fields removed. Seven URL fields on `GroupDetailOptionsBag` removed in favor of the framework's `box.NavigationUrls`. `PanelMode` enum and `substituteEntityKey` helper dropped from `types.partial.ts` (dead / non-canonical). `PageParameterKey.AutoEdit` constant dropped (not consumed in Phase 1; sibling-block convention is to declare only consumed keys).

**Performance / cache-first refinements.** `GroupTypeCache.IsAuthorized` (cache) replaces `new GroupTypeService(RockContext).Get(id).IsAuthorized(...)` (DB hit per render). `IsFundraisingGroupType` resolves via `GroupTypeCache.InheritedGroupTypeId` (cache) instead of `GroupTypeService.Queryable().Any(...)` (DB hit per render); method became static. `GetGroupTypeCacheFor(entity)` helper extracted; `GetBoxOptions` short-circuits on null/Add at the top so per-row visibility flags drop redundant `groupType != null` defensive guards.

**File organization** (spec was silent). The C# block is organized into `Block Attributes` → `Keys` → `Methods` → `Block Actions` → `Helper Methods` regions, locking in a layout that future phases (Save flow, GroupType cascade, edit-mode helpers) can extend without churn. `NavigationUrlKey` static class added to mirror the TS const enum. `BlockActionName` const enum added in TS to replace 5+ magic-string action names and 4 type-union sites. `AddLinkedPageUrl` helper deleted in favor of the canonical inline dictionary initializer (sibling-block consistency). `KeyPlaceholder` private const inlined.

Without those files in `Rock.JavaScript.Obsidian/Framework/ViewModels/Blocks/Group/GroupDetail/`, the TS build fails. ### New latent bugs / TODOs surfaced

In addition to the items in the [New latent bugs / TODOs surfaced during self-review](#new-latent-bugs--todos-surfaced-during-self-review) section above (all of which were either fixed-during or determined not to be real bugs), the user-driven review pass surfaced one accepted tradeoff and one process note:

- **`bag.HasChildGroups` staleness window** (decisions log 2026-05-07, "Collapsed Archive flow from 3 actions to 2"). The Archive prompt-or-not decision is made client-side from a bag value resolved at render time. If a child group is added concurrently between bag render and the user clicking Archive, the user could archive the parent without being prompted about the new child. Worst-case outcome: an active child under an archived parent (inconsistent, fixable, not corrupting). Group-hierarchy edits are rare enough that this was accepted as a tradeoff for the single-round-trip flow. Future-proofing path documented in the decisions log: the `Archive` action could re-check server-side and log a warning. Out of scope for Phase 1.

- **Re-run Rock.CodeGeneration before Phase 2** (decisions log 2026-05-06, "Hand-authored placeholder .d.ts files"). Eight placeholder `.d.ts` files under `Rock.JavaScript.Obsidian/Framework/ViewModels/Blocks/Group/GroupDetail/` were authored by hand to unblock the TS build (the canonical regenerator is a desktop-only WPF tool). Files are byte-compatible with what the tool would emit; regeneration should be a no-op if accurate. Run before Phase 2 work begins to confirm shape parity.

Two earlier "(not a bug)" calls in the section above were subsequently revised during the review pass (`GetCommonEntityBag` per-render auth lookup → cache-only resolution; `IsFundraisingGroupType` per-render query → cache-only resolution). The historical entries are retained for traceability.
